# ADR-0022: Select the color scheme through the settings document

Status: accepted, amended by ADR-0040

Date: 2026-09-05

## Context

`docs/design/2026-09-04-design-brief.md` records that hide approved eight terminal-style palettes and requires the scheme to be user-selectable. `docs/COMMAND_MODEL.md` already names `ISettingsStore` as the sole settings mechanism, but no such port existed: `SettingsDocumentValidator` validated one boolean property and returned an untyped accepted marker that nothing consumed. `Themes/DesignTokens.xaml` held one light-only palette, so the address `TextBox` was unreadable under a dark palette, and ARC-012 forbids a view from carrying a value instead of a semantic key. A scheme is presentation data, but choosing one is a settings decision, so the choice has to enter through the settings boundary and reach the framework only at the composition root (ARC-006).

## Decision

- **One settings document, one location.** `%LOCALAPPDATA%\NeNeCommander\settings.json` is the sole persisted settings document. `WindowsLocalSettingsLocation` is the one named adapter that resolves it, and it is the only file in the repository permitted to read the process environment. The CS-010 conformance scan is narrowed to that file exactly as ADR-0011 narrowed the CS-018 scan, so the executable rule now matches the written rule ("outside named adapters") instead of being blanket.
- **Schema version 1 has three required properties.** `{ "schemaVersion": 1, "showHiddenItems": <boolean>, "colorScheme": "<identifier>" }`. `SettingsDocumentValidator` bounds the text at 65536 characters, rejects a non-object root, rejects any unrecognized name, separates a duplicated property (`UnexpectedProperty`) from a missing one (`Incomplete`) by property count, rejects a non-numeric or unsupported version, rejects a non-boolean visibility, and rejects text that names no approved scheme (`UnknownColorScheme`). A wrongly typed value is never coerced.
- **One outcome vocabulary.** The validator now returns the Application-owned `SettingsReadOutcome` (`SettingsRead(UserSettings)` / `SettingsAbsent` / `SettingsRejected(SettingsReadFailureKind)`) and yields typed `UserSettings` on acceptance. The Infrastructure-owned `SettingsValidationOutcome`, `SettingsValidationAccepted`, `SettingsValidationRejected`, and `SettingsValidationFailureKind` are deleted in the same change so no second vocabulary for the same concern survives (ARC-001).
- **The initial store was read-only.** `WindowsLocalSettingsStore` opens the document for shared reading, rejects it on length before decoding a byte, and normalizes the expected input failures: a missing file or missing directory is `SettingsAbsent`, and a denied or locked file is `SettingsRejected(Unreadable)`. This decision did not create a default document or a write path. ADR-0040 later adds the one explicit settings command and atomic write boundary without changing read behavior or CMD-007.
- **A rejected document keeps the default scheme and is left untouched.** Absent and rejected both resolve to `UserSettings.Default` (`nene-dark`, hidden entries omitted). The product has no mechanism for reporting a settings problem to the user that does not assemble user-facing text in code (CS-025), so the honest behavior is to fail closed to the default and leave the stored bytes exactly as the person wrote them, which is what makes the problem discoverable and correctable. A visible diagnostic belongs to a later Issue that owns the localized resources for it.
- **Closed states, not flags.** `ColorScheme` is a closed sealed record hierarchy of exactly eight members, each carrying its kebab-case `Identifier` and its `ColorSchemeAppearance` (`Dark` / `Light`; `solarized-light` and `nene-light` are `Light`). `ColorScheme.Parse` is the one boundary parse and returns `ColorSchemeAccepted` / `ColorSchemeRejected`. `HiddenItemVisibility` replaces the persisted boolean once it crosses the boundary, so no `bool` reaches an application signature (CS-002).
- **One scheme dictionary per scheme, merged by the composition root.** `Themes/DesignTokens.xaml` keeps only the non-color tokens. `Themes/Schemes/<identifier>.xaml` holds every color for one scheme: eighteen `Color` keys inside the existing `Surface`, `Text`, `Border`, `Focus`, `Selection`, `Status`, and `Operation` families plus one `SolidColorBrush` per color with the `Brush` suffix. No token family is added. `CommanderApplication.StartAsync` reads settings, merges exactly one scheme dictionary into `Application.Resources.MergedDictionaries` before the window is constructed, and sets the window content's `RequestedTheme` from the scheme appearance so framework-provided controls follow the scheme. `ColorSchemeResources.ResolveDictionaryAddress` is one exhaustive closed mapping from scheme to a constant packaged address; persisted text never composes a resource address, and an unmapped scheme throws instead of silently loading nothing.
- **The launch handler owns its task.** A WinUI launch handler cannot await and `async void` is prohibited (CS-016), so `OnLaunched` starts work through the lifecycle owner adopted by ADR-0030. Every expected settings failure is already a typed outcome, so the task faults only on a defect.
- **Dictionary parity is executable.** `eng/conformance.ps1` proves under ARC-012 that `DesignTokens.xaml` defines no color, that `Themes/Schemes` contains exactly one dictionary per identifier declared by `ColorScheme`, that every dictionary declares the same color keys, that every color has exactly one same-named brush, and that every `{StaticResource ...Color}` / `...Brush}` a view references exists in that key set. `NeNeCommander.Architecture.Tests` proves the C# side: eight schemes, unique identifiers, and one distinct dictionary address per scheme named after its identifier. Together these are the "token conformance test" `docs/DESIGN_HANDOFF.md` requires; it did not exist before this change. `eng/prove-gates.ps1` gains three negative proofs: environment access outside the named adapter, a renamed key in one scheme dictionary, and a color declared in `DesignTokens.xaml`.

## Rejected alternatives

- **Writing a default document when none exists.** Convenient for hand editing, but it creates a directory and a file outside the one mutation gateway (ARC-005) and turns a query into a mutation (CMD-007). The schema is documented instead.
- **Repairing or rewriting a rejected document.** SEC-011 requires malformed settings to fail closed. Rewriting would destroy the evidence of what the user actually wrote.
- **One dictionary with eight theme dictionaries keyed by `Light`/`Dark`/`HighContrast`.** WinUI's `ThemeDictionaries` has exactly three keys, so it cannot express eight palettes; using it would force seven palettes into a second mechanism.
- **Composing the dictionary address from the identifier.** `ms-appx:///Themes/Schemes/{identifier}.xaml` reads shorter but lets persisted text reach a resource address. The exhaustive mapping keeps the address list closed even though the mapping looks like an identity.
- **A string `switch` in `ColorScheme.Parse`.** The compiler lowers a string switch to length and character tests whose branches no input set can fully cover, which would have broken the 100% Application branch-coverage ratchet. Parsing by comparing against the published closed set keeps the identifier list and the parse consistent by construction.
- **Keeping `SettingsValidationFailureKind` beside a new Application failure kind.** Two closed vocabularies for one concern, plus a translation nobody can keep exhaustive (ARC-001).
- **Reading the scheme in the window or a view model.** The scheme must be merged before any view resolves a `StaticResource`, and CS-022 forbids the window from making the decision.
- **Proving dictionary parity in an MSTest project.** Reading repository files from a test requires `System.IO` outside the two locations ADR-0011 permits. The canonical gate's conformance scan already owns repository-shape rules and runs before the build.

## Consequences

- The shipped shell renders in `nene-dark` by default; ADR-0040 adds the in-application settings editor while retaining external schema compatibility. An unknown value keeps the default and leaves the file alone.
- `showHiddenItems` is now required, parsed, and typed, but no pane transition consumes `HiddenItemVisibility` yet; the visibility toggle remains a later Issue.
- Adding a scheme is one atomic change: a `ColorScheme` member, its dictionary, and the mapping arm. The conformance scan fails if any of the three is missing.
- Adding a color key means adding it to all eight dictionaries; the scan rejects drift between them.
- `WindowsLocalSettingsLocation.Resolve` throws when the operating system reports a local application-data folder that is not a Windows local path. That is an impossible state, so its branch stays uncovered, which is why Infrastructure keeps a 90% threshold rather than 100%.
- Cancellation of a settings read surfaces as `OperationCanceledException` rather than a closed outcome. The composition root reads with `CancellationToken.None`, so no caller currently observes it; a settings read that a user can cancel would need a `SettingsReadCancelled` variant.

## Migration and removal

`SettingsValidationOutcome`, `SettingsValidationAccepted`, `SettingsValidationRejected`, and `SettingsValidationFailureKind` are removed in this change and replaced by `SettingsReadOutcome` and `SettingsReadFailureKind` in `NeNeCommander.Application.Settings`. The color keys of `Themes/DesignTokens.xaml` are moved, not copied, into the scheme dictionaries; no compatibility dictionary remains. No settings document existed before this change, so there is no stored document to migrate.

## Executable proof

`ColorSchemeTests`, `UserSettingsTests`, `NullGuardTests` (Application and Infrastructure), `InfrastructureBoundaryTests` (ADV-012, including a partially written document, an unknown scheme, a duplicated key, a non-numeric version, and a non-string scheme), `WindowsLocalSettingsStoreTests` on `TestOwnedTemporaryRoot` (complete document, absent document, absent directory, oversized, malformed, denied, and locked, each asserting the stored bytes are unchanged), `ColorSchemeResourceTests`, the ARC-012 scheme-dictionary scan in `eng/conformance.ps1`, its three negative proofs in `eng/prove-gates.ps1`, `docs/quality/GATE_PROOFS.md`, and the canonical gate.
