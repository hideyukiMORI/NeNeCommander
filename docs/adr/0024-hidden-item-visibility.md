# ADR-0024: Decide the visible set of a pane from the persisted hidden-item visibility

Status: accepted

Date: 2026-09-05

## Context

ADR-0022 made `showHiddenItems` a required property of the settings document and turned it into the closed `HiddenItemVisibility` carried by `UserSettings`, but recorded that "no pane transition consumes `HiddenItemVisibility` yet". Nothing read the value: `CommanderApplication.StartAsync` used only `settings.ColorScheme`, and neither `PaneSession` nor `PaneState` had any notion of visibility. ADR-0023 recorded the matching gap on the presentation side: "`DirectoryEntry` has no hidden concept, so `TextHiddenBrush` stays defined and unused until the hidden-item visibility slice."

Two normative rules already describe where this behavior belongs. `docs/COMMAND_MODEL.md` CMD-002 lists hidden-item visibility among the transitions "applied only by `PaneReducer` to an immutable `PaneState`". `docs/FILESYSTEM_BOUNDARIES.md` FS-011 fixes the read side: "Hidden and system entries are reported; visibility is a later pane transition." So the read port must keep returning every entry, and the pane — not the adapter, not the presenter — must decide what is shown.

The missing piece was the fact itself. `DirectoryEntry` carried a path, a provider-reported name, and a closed kind, and nothing else, so no layer above the adapter could tell a hidden entry from an ordinary one. Deriving it from the name would have been a second, wrong mechanism: a leading dot is a Linux convention with no meaning in the Windows namespace, and `$RECYCLE.BIN`, `hiberfil.sys`, `pagefile.sys`, and `swapfile.sys` are hidden because of their attributes, not their spelling.

## Decision

- **Visibility is a reported fact on the entry.** `DirectoryEntry` gains the closed `EntryVisibility` (`Normal` / `Hidden`) and `DirectoryEntry.Create` requires it, so no entry can exist without one. `WindowsLocalDirectoryReader` reports `Hidden` when the enumerated entry carries `FileAttributes.Hidden` or `FileAttributes.System` and `Normal` otherwise. `WslDirectoryReader` reports Linux dot-prefixed names as `Hidden` without treating projected Windows attributes as Linux policy (ADR-0035). No second query touches the provider. The port contract is unchanged: a listing still holds every entry, hidden ones included, and `DirectoryListing` still orders directories first, then by name ignoring case, then ordinally (FS-011, ADR-0010).

- **`PaneState` owns the entries, the visibility, and the derived visible set.** The state holds the location's whole ordered entry snapshot, the `HiddenItemVisibility` in force, and the `VisibleEntries` those two produce. The visible set is computed in the constructor from the other two, so it can never disagree with them, and `PaneState.Create` and the internal `FromListing` reach that one private constructor. `VisibleItems` (a list of paths) is replaced by `VisibleEntries` (the entries themselves), which removes the presenter's need to re-walk the listing to find out what a row shows.

- **`PaneReducer` is the sole decider of what a pane shows.** Movement, paging, first and last, the half-page offset, focus indexing, and selection all address `VisibleEntries` alone. `Navigate` takes the visibility that the new location is listed under. `ApplyHiddenItemVisibility(state, visibility)` is the transition that changes it: `PaneState.WithHiddenItemVisibility` recomputes the visible set and the reducer immediately repairs focus and selection, because deciding where focus lands is a transition and belongs to the reducer (CMD-002, ARC-004).

- **Focus recovery has one rule, used by both transitions.** For a target entry the pane can no longer focus, the recovered focus is: the target itself when it is visible; otherwise the next visible entry in listing order; otherwise the previous visible entry; otherwise no focus. A target the location does not hold at all recovers nothing, which leaves the caller's own default (the first visible entry) in place — the behavior `Navigate` had before this change. `ApplyHiddenItemVisibility` likewise uses the first visible entry when the previous state had no focus, as happens when an all-hidden location is omitted and then shown again. Thus a non-empty visible set always has a focus item before movement. "Next, then previous" is the direction a user reads the pane in, so a hidden focus item hands focus to the row that took its place on screen rather than to one that moved up from below. The same recovery rule serves navigating to the parent out of a hidden directory and toggling the visibility in place.

- **Selection cannot hold what the pane does not show.** `ApplyHiddenItemVisibility` drops exactly the selected items that are no longer visible and keeps the rest. File commands operate on selection when it is non-empty (KBD-004), so a selection that survived out of sight would mean deleting or moving a row the user cannot see.

- **The initial visibility travels as a pane-state value, not as an observer.** `CommanderApplication` already reads `UserSettings` through `ISettingsStore` at startup for the color scheme; it now passes `settings.HiddenItemVisibility` into each `PaneSession` constructor. That is a constructor parameter on a session, which ADR-0019 rejected for the progress observer, and the difference is what the value is. The observer is a collaborator the session calls back into: the App window is that observer and it already holds the session, so injecting it would have required mutable wiring for a cycle, which is why it is passed per call instead. The visibility is not a collaborator. It is a value that belongs to pane state, is needed before the first read completes, and is reported back inside `PaneSnapshot`; there is no cycle to create and nothing to call back into. The session keeps it only as a starting value: `ResolveHiddenItemVisibility` reads the visibility from the listed state when one exists and falls back to the composed value only before the first listing, so the state stays the single owner (ARC-004) and a later toggle cannot be overwritten by a stale session field.

- **The presentation projects the visible set and mutes a shown hidden row.** `PaneListingPresenter` iterates `PaneState.VisibleEntries`, so an omitted entry produces no row at all. `PaneRow` gains the closed `PaneRowVisibility`, which names the semantic brush of the row's name: `TextPrimaryBrush` for a normal entry and `TextHiddenBrush` for a hidden one. The view binds that key through the existing `SemanticResourceConverter`; it holds no colour and makes no decision (ARC-012, CS-023). `PaneStatus` keeps its exact meanings — `Bounded` still means the read stopped at its entry boundary and `EntriesOmitted` still means the path model rejected an entry name — because both are facts about the read, not about the pane's visibility.

- **The session toggle uses `Ctrl+H`.** The design delegation recorded for Issue #72 selects the existing `H` key with the Control modifier. The binding is declared in the canonical keyboard table, emits one `ToggleHiddenItems` intent, and reaches `PaneReducer.ApplyHiddenItemVisibility` through the active `PaneSession`. It is available only in the file-list context; modal and text-entry precedence remains unchanged. The toggle changes session state only; Issue #74 owns persistence.

## Rejected alternatives

- **Filtering hidden entries in `WindowsLocalDirectoryReader`.** Shorter, and it contradicts FS-011 directly: the adapter would decide product policy (CMD-008), the listing would silently disagree with the directory, and every future provider would have to re-implement the same rule.
- **Filtering in `PaneListingPresenter`.** The rows would be right and everything else wrong: movement, paging, selection, and the focus item would still address hidden entries, so `j` would appear to skip rows and `F8` could delete an invisible one. CMD-002 puts the decision in the reducer for exactly this reason.
- **Deriving visibility from the entry name.** A leading dot means nothing in the Windows namespace, and the entries hide actually needs hidden — `$RECYCLE.BIN`, `hiberfil.sys`, `pagefile.sys`, `swapfile.sys` — do not start with one. It would also be a second mechanism the moment a WSL adapter arrives, where the convention is real but the attributes are not.
- **Keeping `PaneState.VisibleItems` as paths and holding the entries only in `DirectoryListing`.** The reducer would need the listing passed alongside the state to recompute a visible set, an invariant nothing could enforce, and the presenter would have to intersect the listing with a path set on every render.
- **A `HiddenItemVisibility` field owned by `PaneSession`.** One line shorter today and wrong the moment the toggle key exists: the session would re-apply its own stale value on the next read and silently undo the transition. Two owners for one value is what ARC-004 forbids.
- **A new `PaneStatus` for "some entries are not shown".** It reads helpful and it lies: `Complete` and `EntriesOmitted` describe the read, and overloading them with a pane preference would make the status mean two different things. If hiding needs a visible indicator, it is a bar or header affordance with its own resources.
- **Adding the toggle keystroke in the original visibility change.** It needed a `docs/KEYBOARD_MODEL.md` revision, a new binding in the canonical table, its generated hint, and the key-map uniqueness proof. It was therefore implemented by the later focused Issue #72 instead of being hidden inside the settings-consumption change.

## Consequences

- With the shipped default (`showHiddenItems: false`) the panes no longer list `$RECYCLE.BIN`, `hiberfil.sys`, `pagefile.sys`, `swapfile.sys`, `System Volume Information`, or any other hidden or system entry, and `C:\` shows what a user expects to see. Setting the property to `true` and restarting brings them back, muted.
- `DirectoryEntry.Create` and `PaneState.Create` each take one more argument, and `PaneSession` takes four. All three sit exactly at CS-013's parameter ceiling; the next value either of them needs will have to be grouped into a type.
- The visible set is materialized once per state, so a visibility change or a location change allocates one extra list of the visible entries. A listing is bounded at 10,000 entries (ADR-0010), so the cost is bounded too.
- `PaneState.Entries` is internal: only the reducer needs the omitted entries, to recover focus. Nothing outside the Application layer can see an entry the pane does not show.
- `PaneReducer.ApplyHiddenItemVisibility` is reached by the `Ctrl+H` binding through `ToggleHiddenItems`; the route changes session state without writing settings.
- The hidden row is distinguished by its name colour alone. The kind icon and the `DIR` label keep their own brushes, so a hidden directory still reads as a directory.
- `DirectoryListing` ordering does not depend on visibility, so showing hidden entries never reorders the entries that were already visible.

## Migration and removal

`PaneState.VisibleItems` is replaced by `PaneState.VisibleEntries` and `PaneState.Create` now takes entries rather than paths; both change in this commit and no compatibility overload remains. `PaneReducer.Navigate` and the `PaneSession` constructor gain their required parameters in the same commit, so no caller can omit the visibility. The `Ctrl+H` binding is a session transition and does not write settings: Issue #74 remains the separate persistence boundary. Existing documents keep working unchanged.

## Executable proof

`PaneReducerTests` (the visible set under both visibilities, movement and first/last over the visible set only, the preferred focus that is hidden recovering forward and then backward, a location whose entries are all hidden, focus kept when it stays visible, focus recovered forward and backward on a visibility change, all-hidden entries restoring focus before movement when shown again, an empty pane, selection losing exactly the items that became hidden, and the toggle intent), `PaneSessionTests` (the composed visibility deciding the first listing and every later read carrying the listed state's own value), `NullGuardTests` (every new required argument), `DirectoryListingTests` (the entry contract with its visibility), `PaneListingPresenterTests` (rows projected from the visible set, the hidden row's `TextHiddenBrush`, the closed visibility resource keys, and the absent-visibility guard), `WindowsLocalDirectoryReaderTests` on `TestOwnedTemporaryRoot` (a hidden file, a hidden directory, a system file, a plain file, a plain directory, and a dot-named file that is reported normal), `KeyboardIntentMapperTests` and `KeyHintPresenterTests` (the `Ctrl+H` binding, context precedence, uniqueness, and localized hint), the ARC-012 presentation resource-key scan in `eng/conformance.ps1`, and the canonical gate.
