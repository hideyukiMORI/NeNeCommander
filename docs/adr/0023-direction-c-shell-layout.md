# ADR-0023: Render the shell as the approved Direction C layout

Status: accepted

Date: 2026-09-05

## Context

`docs/design/2026-09-04-design-brief.md` records that hide approved page 3 of the design canvas — "Direction C", a sharp flat dark-first layout: 6 dip window padding, 3 dip gaps, 3 dip radii, 1 dip lines, a monospace pane header carrying a pane-number badge, 28 dip list rows with a 2 dip left marker and a stroked kind icon, and one full-width 34 dip bar at the bottom that changes tone with the operation state and carries the keyboard hints. ADR-0022 delivered the eight palettes behind that design but changed no layout, so the shell still rendered the pre-design shape: an 18 dip "左ペイン" heading, a framework `TextBox` with a `Header` row, rows that showed only a name, and three loose text blocks plus a name editor at the bottom.

Two rules made this more than a restyle. `docs/CODING_RULES.md` CS-023 requires every spacing, radius, density, and typography value in a view to come from a semantic design resource, so the approved numbers have to become tokens. `docs/KEYBOARD_MODEL.md` KBD-005 requires that "all displayed shortcut hints are generated from the canonical key-map data", and the shell had no hint surface at all: `KeyboardIntentMapper` held its map inside `switch` expressions and exposed nothing, so a hint bar would have had to be typed into XAML and could silently drift from the mapper.

## Decision

- **The approved values are tokens, and the view holds no layout literal.** `Themes/DesignTokens.xaml` keeps only the existing thirteen families (`docs/DESIGN_HANDOFF.md`) and now carries the Direction C values: window padding 6, pane and bar gap 3, pane radius 3, bar radius 3, key-cap radius 2, pane border 1, pane header 34, row 28, row marker 2, kind icon 16, bar 34, name entry 320 × 26, body 13, monospace 12 and 11, and the monospace family (Cascadia Code → Cascadia Mono → Consolas). Three explicit reset tokens (`SpacingNone`, `BorderNoneThickness`, `DensityNone`) exist so that removing framework chrome is also expressed as a token rather than a literal zero. No token family is added; `TypographyPaneTitleSize`, `SpacingPaneInner`, `SpacingAddressBottom`, and `DensityRowMinimumHeight` are removed in the same change because nothing renders them any more.

- **The row's marker, background, and kind are closed presentation values.** `PaneRowMark` becomes four members — `FocusInActivePane`, `Selected`, `FocusInPassivePane`, `Unmarked` — each naming the semantic brush of its 2 dip marker and of its background. `PaneListingPresenter.Present` now takes the pane's `PaneFrame` so it can resolve the single mark: the focus item of the active pane outranks selection, selection outranks the focus item of the passive pane, everything else is unmarked. `PaneRowKind` is the closed rendering of `DirectoryEntryKind`: which of the two shapes the row draws and the localization key of the `DIR` label. The template binds those closed values and computes nothing.

- **The bottom row becomes one operation bar with a closed tone.** `DualPanePresentation` gains `Tone` (`OperationBarTone`) and `KeyHints`. The tone names the bar's surface, foreground, and border brushes plus a closed `OperationBarIcon`: idle for an idle, running, succeeded, or cancelled operation; `AwaitingName` while a name is awaited; `AwaitingConfirmation` while a deletion is confirmed; `Failure` for a rejected request and for a completed operation that was partially completed or rejected. Running progress additionally renders as a fixed twelve-segment bar: `OperationProgressDetail` computes the segments in the presentation (`completed * 12 / total`, floor) so the view performs no arithmetic and a one-item and a thousand-item operation read the same.

- **The key map becomes one table, and the hints are generated from it.** `KeyboardIntentMapper` now maps by scanning one `IReadOnlyList<KeyBinding>` of declared `(context, key, modifier, intent)` entries, and exposes `BindingsFor(context)` over that same list. The `gg` chord is the only stateful entry and is still resolved before the table is consulted. The modal and text-entry contexts keep their existing behaviour of owning their declared keys whatever the modifier state (KBD-002), which is why those two contexts match on the key alone; every other context matches key and modifier. `KeyHintPresenter` declares the ordered intents each context shows — file list: rename, copy, move, create directory, delete, activate other pane, escape; modal: confirm, escape — looks each one up in the canonical table, and emits `KeyHint(keyLabelResourceKey, intentLabelResourceKey)`. The key-cap label is named by `KeyboardKey.LabelResourceKey`, so the label follows the keystroke the mapper really performs; the wording of what the intent does is declared by the presenter. Both labels are resource keys, so no hint text is assembled in code (CS-025). This is not a new canonical mechanism: it is the existing "keyboard mapping" mechanism (`docs/COMMAND_MODEL.md` registry) made readable, so `COMMAND_MODEL.md` gains no row.

- **Vector shapes are framework geometry in the view, not tokens.** WinUI refuses to assign a `Geometry` held in a resource dictionary to `Path.Data` (`XamlParseException: Failed to assign to property 'Microsoft.UI.Xaml.Shapes.Path.Data'`), so a run-time-selected geometry resource is not available. The row template therefore holds both shapes and shows one, and the bar holds the warning triangle and the pen and shows one. `PaneRowKind` exposes `IsDirectory` / `IsFile` and `OperationBarTone` exposes the closed `OperationBarIcon`, so the decision still belongs to the presentation and only the shape lives in the view. Path data is framework geometry under CS-023's documented exception and carries no value that varies by scheme or density, so it adds no token family; the stroke of each shape is a semantic brush the ARC-012 view scan verifies.

- **Two lookup-only converters exist because XAML cannot resolve data-named resources.** `SemanticResourceConverter` resolves a brush key produced by a presentation value into the merged scheme resource, and `LocalizedTextConverter` resolves a localization key into its text. Both perform a lookup and nothing else; neither chooses a key. They live in `NeNeCommander.App` because they touch the framework, and they are the reason the row, hint, and progress templates can bind closed presentation values instead of embedding policy.

- **The pane label strings become the narrator name of the pane region.** The "左ペイン" / "右ペイン" heading and the address `Header` are gone from the visual. `LeftPaneLabel.Text` and `RightPaneLabel.Text` are renamed to `LeftPaneRegion.AutomationProperties.Name` and `RightPaneRegion.AutomationProperties.Name` and applied through `x:Uid` on the pane `Border`, so the wording hide approved keeps working for assistive technology instead of being deleted. `LeftAddress.Header` and `RightAddress.Header` are removed from both resw files because the header row no longer exists; the address keeps its `LeftAddress` / `RightAddress` automation id. The pane number is `LeftPaneNumber.Text` / `RightPaneNumber.Text` so even that glyph is a resource.

- **The framework controls are reduced, not replaced.** The address stays a `TextBox` and the file list stays a `ListView` with framework selection as the focus item; both get a minimal template (a `ScrollViewer` named `ContentElement`, and a `ContentPresenter`) so the scheme, not the framework's own theme brushes, decides how they look, and `UseSystemFocusVisuals` is off because the row itself renders focus. Every automation id in `docs/design/2026-09-04-design-brief.md` is unchanged; `OperationBar`, `OperationProgressSegments`, and `OperationKeyHints` are added.

- **The presentation's colour keys are proved by the canonical gate.** `eng/conformance.ps1` gains an ARC-012 scan: every string literal in `NeNeCommander.Presentation.WinUI` that ends in `Color` or `Brush` must exist in the scheme key set, exactly as view `{StaticResource}` references already must. Reading repository files from an MSTest project would need `System.IO` outside the two places ADR-0011 permits, which is why this proof lives in the gate (the same reasoning ADR-0022 recorded). `eng/prove-gates.ps1` gains the matching negative proof and `docs/quality/GATE_PROOFS.md` the matching row.

## Rejected alternatives

- **Typing the key hints into XAML.** Shorter, and immediately wrong: KBD-005 exists because a hint that outlives its binding lies to the user. Generating them from the mapper's own table makes drift impossible.
- **Keeping the mapper's `switch` expressions and adding a second, parallel list of bindings for the hints.** Two declarations of one key map is exactly the competing mechanism ARC-001 prohibits.
- **Putting the key-cap wording on `KeyBinding`.** The binding would then carry presentation wording for twenty-four keystrokes that are never displayed, and its constructor would exceed CS-013's parameter ceiling. The key identity names its own cap label instead, and only the displayed intents carry wording.
- **A `DataTemplateSelector` or a value converter that decides the icon.** Both move "what a directory looks like" out of the closed presentation and into the view layer, which is what ARC-012 and CMD-003 forbid. The two-shape template keeps the decision in `PaneRowKind`.
- **A geometry resource dictionary keyed by name.** The natural design, and the framework rejects it: `Path.Data` cannot take a `Geometry` from a resource dictionary. Discovered at run time, not in the build.
- **Grouping the bar into an `OperationBarPresentation` record.** Cleaner on paper, but `DualPanePresentation` is one flat render-ready projection and regrouping it would churn every existing presentation test without changing a single behaviour.
- **Computing the progress segments in the view.** Arithmetic in a template is untestable and would have to be repeated by any other host.
- **Deleting the pane label strings.** The words are still the only name a screen reader can give the two regions.

## Consequences

- The shell renders the approved layout in all eight schemes; only `nene-dark` and `solarized-light` were checked on the machine.
- `PaneListingPresenter.Present` now requires the pane's frame. Every caller passes it; there is no overload that guesses.
- The idle bar shows no numbers after a completed operation, while the canvas artboard shows the final `12/12`. Keeping the last progress after completion would mean the session held a finished operation's progress, which no closed activity carries today.
- The running progress numbers use the tone's foreground rather than the accent the canvas uses for them. One tone drives every colour in the bar; a second colour for numbers would be a rule the tone does not express.
- Hidden entries are still not distinguished: `DirectoryEntry` has no hidden concept, so `TextHiddenBrush` stays defined and unused until the hidden-item visibility slice.
- `KeyboardKey` now names a label resource for all twenty-four identities, including `Other`, whose label is empty because no binding declares it.
- The two lookup converters are the only new framework-boundary code; both are in the App project, which ADR-0008 excludes from the coverage denominator.

## Migration and removal

`PaneRowMark.Unselected`, `PaneRow.IsSelected`, `PaneListingPresenter.Present(PaneSnapshot)`, and the four removed design tokens are deleted in this change; no compatibility path remains. `LeftPaneLabel.Text`, `RightPaneLabel.Text`, `LeftAddress.Header`, and `RightAddress.Header` are removed from both resource files in the same change, and the pane wording moves to the two new automation-name resources.

## Executable proof

`KeyboardIntentMapperTests` (every existing mapping unchanged, each declared binding maps to its intent, no context declares a keystroke twice, the declared counts, the key-cap label resources), `KeyHintPresenterTests` (the exact ordered hints for the file-list and modal contexts, no hints elsewhere, every hint's key comes from a declared binding), `PaneListingPresenterTests` (focus in the active pane, focus in the passive pane, selection, selection under a focused row, the mark and kind resource keys), `DualPanePresenterTests` (tone for name entry, delete confirmation, request rejection, partial completion, success and cancellation, the twelve segments at zero, half, and full, and the key hints of both contexts), the ARC-012 presentation resource-key scan in `eng/conformance.ps1` with its negative proof in `eng/prove-gates.ps1`, and the canonical gate.
